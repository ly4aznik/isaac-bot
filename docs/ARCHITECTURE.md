# Архитектура Isaac Bot

## 1. Цель

Бот должен самостоятельно начинать обычный ран, принимать решения в реальном
времени и постепенно научиться стабильно завершать забеги. Разработка идёт от
детерминированных правил к обучаемой политике, но среда, протокол действий,
метрики и запись эпизодов остаются общими.

Главный принцип: Lua отвечает только за точное взаимодействие с игрой, Python —
за состояние, планирование, обучение и эксперименты.

## 2. Общая схема

```text
┌──────────────────────── The Binding of Isaac ────────────────────────┐
│                                                                     │
│  Lua mod                                                            │
│  ├─ ObservationCollector: игрок, враги, снаряды, двери, предметы    │
│  ├─ ActionInjector: движение, стрельба, бомба, активный предмет     │
│  ├─ EpisodeLifecycle: начало, смерть, переход комнаты, победа       │
│  └─ SafetyWatchdog: отпускает управление при пропаже Python          │
│                         │ UDP localhost                              │
└─────────────────────────┼───────────────────────────────────────────┘
                          │
┌─────────────────────────▼ Python ───────────────────────────────────┐
│  Runtime                                                            │
│  ├─ GameSupervisor: запуск, новый ран, восстановление после смерти  │
│  ├─ BridgeClient: протокол, heartbeat, синхронизация кадров         │
│  └─ EpisodeRecorder: наблюдения, действия, награды, события         │
│                                                                     │
│  Intelligence                                                       │
│  ├─ StateBuilder: сырые сущности → нормализованное состояние        │
│  ├─ TacticalPolicy: уклонение, прицеливание, локальное движение     │
│  ├─ RoomPlanner: двери, зачистка, подбор предметов                   │
│  ├─ RunPlanner: маршрут этажа, ресурсы, боссы, концовка              │
│  └─ PolicySelector: rule-based / imitation / RL / hybrid            │
│                                                                     │
│  Evaluation                                                         │
│  ├─ Metrics: урон, комнаты, этажи, время, победы                     │
│  ├─ ScenarioRunner: повторяемые комнаты и seed-наборы                │
│  └─ ReplayAnalyzer: разбор провалов и сравнение версий               │
└─────────────────────────────────────────────────────────────────────┘
```

## 3. Разделение ответственности

### Lua-мод

Lua должен работать быстро и предсказуемо. Он не принимает стратегических
решений и не хранит модель.

Обязанности:

- выдавать уникальный номер кадра и идентификаторы рана, этажа и комнаты;
- экспортировать состояние игрока, геометрию комнаты и значимые сущности;
- принимать атомарный вектор действий;
- сообщать события: урон, убийство, подбор, вход в комнату, смерть, победа;
- поддерживать команды `new_run`, `restart`, `pause_agent`;
- выключать ввод агента, если heartbeat пропал;
- версионировать протокол и отклонять несовместимые пакеты.

### Python runtime

Runtime отделяет алгоритм от технического управления игрой. Любая политика
получает одинаковый `Observation` и возвращает одинаковый `Action`.

Рекомендуемый интерфейс:

```python
class Policy(Protocol):
    def reset(self, episode: EpisodeInfo) -> None: ...
    def act(self, observation: Observation) -> Action: ...
```

Игровой цикл:

```text
получить состояние → обновить память → выбрать цель → вычислить действие
→ отправить действие → записать transition → обновить метрики
```

### Интеллект в три уровня

1. **Тактика, 30–60 Гц.** Уклонение от ближайших угроз, прицеливание и
   безопасная позиция.
2. **План комнаты, 2–10 Гц.** Выбор цели, двери, предмета, безопасной области.
3. **План рана, по событиям.** Маршрут этажа, ключи/бомбы/монеты, магазины,
   сокровищницы, босс и долгосрочная ценность предметов.

Такое разделение не заставляет одну нейросеть одновременно учиться избегать
пули и решать, стоит ли тратить ключ.

## 4. Представление состояния

Наблюдение должно быть независимым от разрешения экрана и содержать:

- игрок: позиция, скорость, здоровье, ресурсы, характеристики, предметы;
- комната: границы, тип, состояние зачистки, двери и препятствия;
- динамические сущности: тип, вариант, позиция, скорость, размер, здоровье;
- снаряды и лазеры: позиция, скорость, направление, опасный радиус;
- pickups и pedestals: тип, позиция, стоимость/доступность;
- контекст: этаж, seed, номер комнаты, прошедшие кадры;
- память: посещённые комнаты и последние принятые решения.

Для нейросети полезны две параллельные формы:

- список объектов с относительными координатами;
- пространственная сетка комнаты с каналами угроз, стен, целей и pickups.

Сырые игровые ID сохраняются в записи эпизода, но политика получает
нормализованные признаки.

## 5. Пространство действий

Непрерывная часть:

- `move_x`, `move_y` в диапазоне `[-1, 1]`;
- `shoot_x`, `shoot_y` в диапазоне `[-1, 1]`.

Дискретная часть:

- бомба;
- активный предмет;
- карта/пилюля;
- drop;
- взаимодействие/подтверждение, если оно требуется интерфейсом.

На ранних этапах тактический контроллер формирует непрерывные оси сам. Для RL
их можно дискретизировать до 8 направлений плюс `idle`, чтобы ускорить обучение.

## 6. Награда и метрики

Награда нужна только обучаемой политике; метрики используются всегда.

Базовая награда:

- большой плюс за завершение комнаты, этажа и победу;
- небольшой плюс за нанесённый урон и полезный pickup;
- большой штраф за полученный урон и смерть;
- слабый штраф за время, чтобы не стоять на месте;
- штраф за бессмысленную трату бомбы/ключа;
- потенциальная награда за снижение расстояния до выбранной цели.

Нельзя оптимизировать только убийства: агент может научиться фармить или
затягивать бой. Главные метрики версии:

- доля очищенных тестовых комнат;
- урон на комнату;
- среднее число пройденных комнат и этажей;
- процент побед на фиксированном наборе seed;
- время принятия решения и пропущенные кадры;
- число аварий протокола/зависаний.

## 7. Стратегия обучения

Рекомендуется гибридный путь:

1. геометрические правила создают первого работающего агента;
2. человек или rule-based агент записывает демонстрации;
3. imitation learning обучает базовую политику;
4. reinforcement learning улучшает её на повторяемых сценариях;
5. стратегические решения долго остаются rule-based;
6. итоговая система выбирает между правилами и моделью по уверенности.

Обучать сразу полное прохождение с пикселей слишком дорого и плохо объяснимо.
Lua API даёт структурированное состояние, поэтому сначала следует использовать
его; изображения можно добавить позже как отдельный исследовательский трек.

## 8. Воспроизводимость

Каждый эксперимент хранит:

- версию кода и протокола;
- конфигурацию политики;
- seed игры и список сценариев;
- версию модели и случайный seed обучения;
- JSONL/Parquet запись эпизода;
- итоговые метрики;
- при необходимости видео или список временных меток для монтажа.

Версия считается улучшением только после сравнения на одном и том же закрытом
наборе seed. Красивый единичный ран не заменяет benchmark.

## 9. Предлагаемая структура проекта

```text
isaac_bot/
  bridge/          # протокол и транспорт
  runtime/         # supervisor, игровой цикл, lifecycle
  state/           # схемы и преобразование наблюдений
  policies/        # random, rules, imitation, RL, hybrid
  planning/        # room planner и run planner
  recording/       # эпизоды, replay, datasets
  evaluation/      # сценарии, метрики, benchmark
  cli/             # команды запуска и экспериментов
game/mods/isaac_bot_bridge/
  main.lua         # тонкий игровой адаптер
configs/           # воспроизводимые конфигурации
runs/              # локальные результаты, не исходный код
docs/              # архитектура, roadmap и журнал выпусков
tests/
```

## 10. Технические риски

- Lua API может не раскрывать отдельные атаки или геометрию — нужен контракт
  `unknown entity`, а не падение сборщика.
- UDP допускает потерю пакетов — каждый пакет содержит frame/sequence, действия
  периодически повторяются, устаревшие пакеты игнорируются.
- Игровая скорость зависит от FPS — решения привязываются к номеру кадра.
- Моды могут отключать достижения; эксперименты следует вести на отдельном
  сохранении и не смешивать с личным прогрессом.
- Обновление игры может менять ID и API — smoke-тест протокола обязателен перед
  серией экспериментов.
